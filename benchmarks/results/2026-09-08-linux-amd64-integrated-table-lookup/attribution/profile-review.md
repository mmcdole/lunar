The five paired CBOR load profiles support further investigation of the fallback table path, but do not isolate the added array guard as the cause of the measured regression. The separate unprofiled timing result remains the speed comparison.

All ten runs have the expected source revision, binary hash, input and codec hashes, complete output oracle, and alternating pair order. Main contributes 886 samples / 8.86 seconds of sampled CPU; the shared-array candidate contributes 896 samples / 8.96 seconds. Candidate-minus-main sampled CPU by pair is +10, +10, +50, +30, and 0 milliseconds. Each sample represents 10 milliseconds; each lane performs five loads. These totals are attribution data, not a new speed gate.

The exact profile decoder's exclusive and cumulative function weights agree with pprof for every reported function: 229 functions in main and 261 in the candidate. The [aggregate report](profile-analysis/REPORT.md) includes every run's absolute CPU total, overlapping cumulative shares, and the largest exclusive costs in either lane. All function weights are retained in [summary.json](profile-analysis/summary.json).

The table evidence is specific:

- `executeRawTableSet` increases from 230 to 340 milliseconds of cumulative sampled CPU across the five loads. Its annotated call into the unchanged `rawSetNormalizedSlot` fallback increases from 170 to 280 milliseconds. That accounts for the same 110-millisecond difference within this sampled call tree. It does not identify which instruction or downstream operation caused that difference.
- `rawSlot` increases from 50 to 80 milliseconds cumulative. The candidate's `existingArrayIndex` has four samples / 40 milliseconds, all attributed through the raw read in the annotated listing. Its normalized fallback has 30 milliseconds versus 20 milliseconds in main.
- Across all callers, `normalizeTableKey` changes from 30 to 50 milliseconds cumulative. The candidate's VM write guard has no samples attributed to its new lines. Absence of samples at that resolution does not establish zero cost.
- The corresponding cumulative shares are 2.60% → 3.79% for `executeRawTableSet`, 0.56% → 0.89% for `rawSlot`, and 0.34% → 0.56% for `normalizeTableKey`. These overlap and cannot be added or treated as removable time.

Costs outside the changed table paths also shift. Unchanged `stringByte` grows from 160 to 310 milliseconds cumulative, `stringSub` from 680 to 790, while `commitTailCall` falls from 430 to 230. `planFunctionCall` is 630 versus 650 milliseconds, and `publishFunctionCall` 480 versus 550. Automatic semantic collection is nearly unchanged at 170 versus 180 milliseconds; its heap measurement is 110 milliseconds in each lane. This distribution prevents a source-level claim that the additional predicate alone explains the workload regression. It also leaves substantial call and string work visible rather than presenting table normalization as the whole cost.

The [main](profile-analysis/baseline-annotated.txt) and [candidate](profile-analysis/candidate-annotated.txt) source listings use the exact clean checkouts recorded by the collector. Profile sampling, inline attribution, instruction layout and profiling overhead limit precision at individual lines. Count instrumentation can establish which paths execute and how often; it cannot assign time to the failed guards. An integrated fallback design would need its own whole-program and CBOR measurements before any performance claim.
